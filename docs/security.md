# Учётные данные и проверка секретов

Runtime credentials не хранятся в properties и не выводятся обработчиком входа.
Они передаются через окружение; значения по умолчанию для них не предусмотрены.
Тестовые H2-данные и локальный Maven preset используют отдельные фиктивные настройки.

Удаление текущих литералов не отзывает уже опубликованные credentials. История Git
содержит исходные значения; владелец подтвердил отзыв или замену обоих паролей в
[issue #2](https://github.com/Kenedy228/online_reader/issues/2). Работоспособность старых паролей не проверялась.

## Окружение обычного запуска

| Переменная | Назначение |
| --- | --- |
| `SPRING_DATASOURCE_URL` | JDBC URL выбранной локальной PostgreSQL |
| `SPRING_DATASOURCE_USERNAME` | Имя пользователя БД |
| `SPRING_DATASOURCE_PASSWORD` | Пароль БД |
| `SPRING_PROFILES_ACTIVE` | Явно выбранный `local` или `production` |
| `SPRING_MAIL_HOST`, `SPRING_MAIL_PORT` | Локальный Mailpit, без auth и credentials |
| `ONLINE_READER_STORAGE_ROOT` | Каталог хранения; в `production` обязателен абсолютный путь |

Spring Boot не загружает `.env` автоматически. Можно создать приватный файл
из пустого шаблона и экспортировать значения перед запуском:

```sh
umask 077
cp .env.example .env
# Заполнить .env локально; shell-символы в значениях заключить в одинарные кавычки.
set -a
. ./.env
set +a
```

Команда `.` исполняет shell-код: загружайте только собственный доверенный файл.
В IDE задавайте те же переменные через настройки запуска. Не передавайте пароль
аргументом команды, не публикуйте env-файл, историю shell или дамп окружения.
`.gitignore` исключает `.env`; в `.env.example` credentials оставлены пустыми.

Для ознакомительного запуска используйте `./mvnw spring-boot:test-run@local`:
он использует профиль `test` с H2 и localhost SMTP из тестового classpath.
EnvironmentPostProcessor принудительно ставит эти настройки выше runtime-окружения
до создания beans. При отсутствии тестового ресурса (в обычном JAR) `test`
отклоняется. Проверки не обращаются к внешним БД или SMTP.

Runtime-профили `local` и `production` разрешают только локальный Mailpit,
внешний SMTP host и TLS/auth overrides отклоняются. SMTP credentials не требуются.
Mailpit в Compose не имеет relay/forward конфигурации; release checks и rDNS
выключены, порты UI/SMTP опубликованы на loopback, inbox временный.
Проверки Spring Mail и очистка — [mail.md](mail.md).
Параметры профилей, лимитов, путей и таймаутов — в README и `.env.example`.
`production` предназначен для локальной проверки конфигурации, не для деплоя.
Ошибки валидации конфигурации содержат имена ключей без введённых значений.
Не включайте debug/trace или вывод SQL для диагностики с реальными credentials.

## Проверка перед коммитом

Установите [Gitleaks v8.30.1 из официального релиза](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1).
Go, Docker или дополнительный Python-проект для проверки не требуются:
используется готовый бинарник в `PATH`.

```sh
sh scripts/check-secrets.sh
sh test/security/check-secrets.sh
```

Первый скрипт по умолчанию проверяет только staged-изменения, поэтому локальный
игнорируемый `.env` оператора не блокирует коммит. Второй проверяет безопасные
контроли и семь небезопасных fixtures в staged/snapshot режимах без реальных секретов.
Код возврата `3` означает находку, прочие ненулевые коды — ошибку проверки.
Значения в выводе маскируются; не отключайте проверку ради зелёного результата.

Для автоматической локальной проверки можно подключить `.githooks/pre-commit`:

```sh
git config --local core.hooksPath .githooks
```

Если уже используются свои hooks, включите команду проверки в существующий
pre-commit вместо замены `core.hooksPath`. Хук не подключается автоматически.

CI запускает проверку fixtures и `sh scripts/check-secrets.sh snapshot` из чистого
checkout. Snapshot-режим сканирует каталог, включая локальные неотслеживаемые
файлы; он предназначен прежде всего для CI. Workflow использует закреплённые
checkout action и Gitleaks, проверяет SHA-256 архива и не публикует отчёты с данными.
Это только secret check; полный quality pipeline остаётся задачей #20.

Базовые правила Gitleaks дополнены проверками Spring properties и credential env
assignments. Исключения разрешены только для известных H2 fixture-значений в
конкретных тестовых properties, а не для файла целиком. Сканер эвристический:
review должен учитывать кодирование, новые форматы конфигурации и пути передачи
данных. Не добавляйте allowlist для настоящих credentials.

## Опубликованные credentials и история

Владелец учётных записей должен:

1. Отозвать или сменить опубликованные SMTP- и DB-пароли, проверить переиспользование
   в других системах и обновить своё окружение.
2. Подтвердить факт ротации в issue #2 без публикации новых или старых значений.
3. При необходимости отдельно согласовать очистку истории, копий и форков.
   Переписывание Git history этим исправлением не выполняется и не заменяет отзыв.

История проверяется отдельно, с маскированием:

```sh
gitleaks git --config .gitleaks.toml --redact --no-banner --log-opts=--all .
```

Исторические находки ожидаемы, пока старые коммиты доступны. CI проверяет чистый
текущий снимок; успешный check не означает очищенную историю или отозванные пароли.
