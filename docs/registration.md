# Регистрация аккаунта

GET/POST `/registration` обслуживает `RegistrationController`. Форма передаёт
только username, email, password и confirmPassword в отдельный DTO. Серверная
Bean Validation действует в MVC и на публичном методе RegistrationService;
HTML-проверки помогают пользователю, но не определяют допуск. Повторяющиеся
параметры полей отклоняются: несколько паролей не склеиваются в другой пароль.

## Правила MVP

Владелец выбрал обязательный уникальный email для новых регистраций (#16).

| Поле | Правило |
| --- | --- |
| username | 3–50 ASCII букв/цифр/`_.-`, первый символ — буква/цифра; trim по краям, регистр значим |
| email | обязателен, ASCII без пробелов внутри, корректный email по Bean Validation, максимум254; trim и lowercase Locale.ROOT всего адреса |
| password | минимум15 Unicode code points, максимум72 байта UTF-8; не обрезается и не нормализуется; не может состоять только из пробелов |
| confirmPassword | обязательное точное совпадение; не сохраняется в БД |

Правила username относятся к новым регистрациям; старые имена и хэши не
переписываются. Email приложение считает одинаковым независимо от регистра
**всего** адреса, включая local part; provider-specific точки/`+`-aliases не
объединяются. Интернациональные адреса с не-ASCII символами пока не принимаются;
ASCII punycode-домен допустим, если проходит валидатор. Для login используется
username, email не является альтернативным идентификатором входа.

Минимум15 символов выбран для пароля без MFA по
[OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
Максимум72 **байта** сохраняет BCrypt-контракт #14; длинный ввод отклоняется,
не усекается. Для не-ASCII паролей лимит в символах ниже: например36 русских
букв или18 четырёхбайтных emoji. Произвольные правила состава/периодическая смена
не вводятся. Это ограниченная политика текущего BCrypt, не заявление о полном
соответствии NIST/ASVS.

## Запись и ошибки

RegistrationService кодирует пароль штатным PasswordEncoder BCrypt cost12,
затем выполняет один параметризованный JPA native INSERT `ON CONFLICT DO NOTHING`
в транзакции. Username/email защищены UNIQUE в БД. Предварительная проверка
`exists()` не используется как защита от гонки. При коллизии запись не изменяется,
возвращается обычный отказ без exception, SQL и email в логе. Другие ошибки БД
не превращаются в успешную регистрацию. Вставка создаёт только обычный аккаунт
с разрешающими флагами; role/passwordHash/account flags из HTTP не привязываются.

Ошибки ввода связаны с полями и доступны через aria-describedby/alert. При
коллизии username и email получают одно обобщённое сообщение без указания,
какое поле занято. Это не скрывает сам факт отклонения комбинации: при
подтверждении email потребуется отдельно спроектировать anti-enumeration flow.
В model остаются только username/email и безопасные ошибки; оба пароля и их
rejectedValue удаляются, password inputs всегда пустые. Сессия и redirect не
содержат credentials. Логирование request body/Bean Validation exceptions с
вводом на реальном runtime включать нельзя.

Успешный POST перенаправляет на `/login?registered` (Post/Redirect/Get).
Автоматического входа нет. Уже вошедший пользователь перенаправляется на `/`
без создания нового аккаунта. CSRF включён для POST; query-параметры GET не
привязываются к DTO.

Email сейчас **не подтверждён**: письмо, verification token, восстановление и
смена email не входят в #16. Не считайте этот адрес доказательством владения и
не используйте его для выдачи доступа или восстановления до отдельной реализации.
Письма регистрации не отправляются, настройки Mailpit остаются прежними.

## Ограничение публичной регистрации

Отдельный limiter использует алгоритм #14: после CSRF, до binding/валидации/BCrypt,
по remote address, без доверия X-Forwarded-For. Он учитывает все прошедшие CSRF
POST, в том числе успешные и некорректные; не расходует login budget.

| Переменная | Default | Допустимо |
| --- | --- | --- |
| `REGISTRATION_MAX_ATTEMPTS` | `5` | 1–100 |
| `REGISTRATION_WINDOW` | `60s` | 1 секунда–15 минут |
| `REGISTRATION_MAX_CLIENTS` | `1024` | 1–4096 |

При отказе ответ429 с Retry-After. Состояние ограничено, активные адреса не
вытесняются, истёкшие окна освобождаются при новом запросе. Ограничения общего
NAT, одного процесса, перезапуска/нескольких узлов и заполнения ёмкости те же,
что в [authentication.md](authentication.md). Это не защита от распределённого
создания аккаунтов; внешняя граница сети/доверенные proxy не входят в работу.

## V3 и старые аккаунты

V3 добавляет `users.email varchar(254)` с UNIQUE и CHECK канонического вида
(lowercase/trim/nonempty). Для старых строк email остаётся NULL: выдуманный адрес,
удаление аккаунтов или принудительная блокировка входа не используются.
Новые HTTP-регистрации и RegistrationService обязательно требуют email;
nullable-столбец сохраняется для legacy, БД сама не отличает старую строку от
новой вставки сторонним SQL. Admin/email/roles provisioning не добавляются.

V1/V2 неизменны. Перед обновлением — backup и восстановленная отдельная копия
по [database.md](database.md). При необходимости позже заполнить legacy email
нужно получить реальные адреса от владельцев и разрешить коллизии отдельной
процедурой; запрет NULL потребует новой миграции после этого. Откат приложения
не должен удалять собранные email; автоматической down-миграции/очистки нет.

## Проверки

`make check`: серверная политика, успешная регистрация и вход, дубли, все
неверные поля/Unicode byte boundaries, privilege injection, очистка паролей в
DTO/BindingResult/HTML/логе/сессии, CSRF и отдельный лимит. H2 включён в PostgreSQL
mode только для native INSERT; это не подтверждает PostgreSQL semantics.
`make test-integration`: disposable PostgreSQL17 с настоящим Spring application,
RegistrationService/JPA/транзакциями; конкурентная регистрация по username/email
имеет ровно одного победителя, не меняет его hash и не ломает последующие записи.
Миграционные тесты отдельно проверяют V2→V3, legacy NULL/flags/hash и UNIQUE/CHECK.
Browser smoke: реальная регистрация→вход→выход, дубли/связи ошибок/пустые пароли,
клавиатура/toggle/focus,320px/200% и scoped axe. Используются синтетические данные
и только собственный loopback preview; внешние аккаунты/БД/SMTP не затрагиваются.
