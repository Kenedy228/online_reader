# Вход и сессия

`POST /login` обслуживает Spring Security formLogin, а не MVC controller.
`JpaUserDetailsService` загружает только `users`, выдаёт `ROLE_USER`, для Admin
добавляет `ROLE_ADMIN` и учитывает
`enabled`, `account_non_locked`, `account_non_expired`, `credentials_non_expired`.
Таблица `admin` не является альтернативным способом входа. Регистрация —
[registration.md](registration.md),
роли, процедура оператора и матрица — [authorization.md](authorization.md);
owner-проверки книжных ресурсов в #17 ещё не завершены.
Seed-аккаунтов, универсального пароля и публичного provisioning нет; роль
существующего users назначает только оператор БД по authorization.md.

## Пароли и отказ входа

Используется штатный `DelegatingPasswordEncoder` с единственным BCrypt encoder,
work factor 12, случайной солью и префиксом `{bcrypt}`. Fallback, `{noop}` и
сравнение открытого текста отсутствуют. Поля Java называются `passwordHash`;
столбцы `password` расширены до varchar(255). Bean Validation и PostgreSQL CHECK
разрешают только `{bcrypt}$2a$12$…` (также 2b/2y). Новые сценарии записи обязаны
вызвать внедрённый PasswordEncoder до сохранения; повторно кодировать hash нельзя.

Username обрезается по краям штатным фильтром, предел — 50 code points; регистр
значим. Непустой пароль ограничен 72 **байтами UTF-8** до BCrypt: превышение
отклоняется, а не молча усекается. Это ограничение алгоритма; для новых регистраций дополнительно требуется
минимум15 Unicode code points (legacy login этим минимумом не ограничен). Ограничение всей HTTP-формы отдельно
задаётся контейнером; фильтр не читает и не сохраняет произвольное тело запроса.

Неверный пароль, неизвестный пользователь и любой запрещающий флаг аккаунта
дают одинаковый redirect `/login?error`. Проверка статусов выполняется после
сравнения BCrypt; неизвестное имя использует штатный dummy hash провайдера.
Это уменьшает различия по времени, но не обещает постоянное время всей БД/HTTP.
Один явный ProviderManager исключает повторную проверку через parent manager.
Причина отказа, username и пароль не сохраняются в session/model; GET формы
всегда пустой, query credentials не отражаются в HTML. Приложение не логирует
credentials, hash или исключение входа. Не включайте request-body/security TRACE
logging на runtime с пользовательскими данными.

## Сессия и CSRF

После успешного входа создаётся security context и меняется идентификатор
существующей сессии; redirect всегда `/`, сохранённого произвольного URL нет.
Logout — только `POST /logout` с CSRF: context удаляется, сессия инвалидируется,
JSESSIONID удаляется. GET не выполняет выход. CSRF включён для входа и выхода;
отклонённые CSRF-запросы не расходуют бюджет BCrypt.

Cookie `JSESSIONID`: HttpOnly, SameSite=Lax, только cookie tracking, без
персистентного сохранения сессий. Local/test допускают HTTP (Secure=false),
production требует Secure=true и отдельно обеспеченный HTTPS. TLS/деплой в эту
задачу не входят. Доверие forwarded headers выключено; приложение не извлекает
IP из произвольного X-Forwarded-For. Перед reverse proxy потребуется отдельное
решение о доверенных прокси, реальном адресе и HTTPS.

| Переменная | По умолчанию | Допустимо |
| --- | --- | --- |
| `SESSION_TIMEOUT` | `15m` | 1–60 минут простоя |
| `LOGIN_MAX_ATTEMPTS` | `10` | 1–100 запросов |
| `LOGIN_WINDOW` | `60s` | 1 секунда–15 минут |
| `LOGIN_MAX_CLIENTS` | `1024` | 1–4096 адресов |

Runtime guard проверяет настройки до подключения к БД. Контейнер округляет
session timeout до целых минут; используйте целые минуты. Истечение не обязано
немедленно отозвать сессии на других узлах: общего session store нет.

## Ограничение попыток

Каждый прошедший CSRF POST входа резервирует попытку до проверки credentials,
включая успешный вход и некорректный ввод. Счётчик не сбрасывается успешным входом.
Бюджет — фиксированное окно по `getRemoteAddr()` внутри одного процесса,
монотонные часы; username/пароли не сохраняются. Доступ синхронизирован,
количество адресов и размер ключа ограничены. Истёкшие записи очищаются при
следующем запросе. Активные записи не вытесняются новыми адресами: при заполнении
ёмкости новые адреса получают отказ до освобождения места. Ответ — 429 с
`Retry-After`, без отражения ввода.

Общий NAT разделяет бюджет. Перезапуск обнуляет лимит; несколько экземпляров
не делят состояние; распределённую атаку и DDoS это не решает. Для публичного
развёртывания нужны отдельные решения на границе сети и наблюдаемость (#27),
без расширения этой карты неограниченными username/IP counters.

## V2 и восстановление старых данных

V1 не изменяется. V2 транзакционно расширяет столбцы обоих типов аккаунтов,
добавляет `{bcrypt}` только к распознанным legacy BCrypt cost12 и вводит CHECK.
Хэш не пересчитывается, данные/флаги/связи аккаунтов не удаляются.
Открытый текст, другой cost/алгоритм или повреждённое значение останавливают
миграцию целиком; частично обновлённой схемы/префиксов не остаётся.

Перед обновлением сделайте backup и проверьте восстановление отдельной копии
по [database.md](database.md). Если миграция отказала, не обходите CHECK,
не правьте V1/history и не кодируйте автоматически найденные строки как пароли:
неизвестно, являются ли они паролями или хэшами. Сохраните старую БД и согласуйте
отдельную процедуру сброса/переноса аккаунтов без раскрытия значений. Не удаляйте
записи ради старта. Для новой пустой БД V1→V2 выполняются автоматически.

## Проверки

`make check`: JPA/encoder, все статусы отказа, CSRF/logout, лимит/параллельность,
UTF-8 границы, runtime config и настоящий HTTP Tomcat: cookie, смена ID,
настроенные15 минут простоя через ServletContext, невозможность replay после logout.
Фактическое ожидание истечения15 минут не выполняется. `make test-integration`:
PostgreSQL CHECK, V1→V2 с сохранением данных и полный rollback при неизвестном
значении; Mailpit. Проверки используют только синтетические аккаунты и disposable
БД. H2 suite не заменяет PostgreSQL constraints; HTTPS production cookie policy
проверяется конфигурацией, не запуском внешнего TLS-сервера.
